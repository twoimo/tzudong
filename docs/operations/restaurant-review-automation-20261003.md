# 맛집 검수 자동 운영 · 구현과 검증

최신 사용자 지시인 “승인까지 자동 운영해”를 적용한다. 기존 장기 목표의 전체 UI·파이프라인·OCR·스토리보드·운영 반영 범위는 유지한다. 이 문서는 자동 운영 부분의 증빙이며 전체 목표 완료 선언이 아니다.

## 동작과 보호

`/admin?module=restaurants`에 정책, 후보 미리보기, 시작·중지·즉시 실행, 최근 처리 수, 보류 사유와 상세 조회를 연결했다. 기본 회당 50건·하루 승인 50건, 각각 최대 200건이다. 시작은 데이터 revision과 정책 version에 묶인 미리보기 확인 후 적용한다. 분류·조건부 변경·읽기 확인·감사 기록은 하나의 DB 트랜잭션이다.

자동 승인 조건은 평가값과 근거, 주소·좌표, 위치 일치와 독립 위치 근거, 상호와 원본 식별자, 중복 검사 조건의 **교집합**이다. 평균 점수나 추정 확률로 누락된 조건을 보충하지 않는다. 기존 관리자·사용자 수정과 승인·보류·삭제 결정은 보호한다. 불완전한 평가 근거는 재검수 큐에 넣고 충돌·위치 확인 항목은 보류한다. 감사 테이블에는 식별자·고정 사유·상태만 저장하고 상세 원문을 복제하지 않는다. 화면 상호는 현재 맛집 행에서 조회한다.

같은 요청 ID는 같은 실행 결과를 읽는다. 같은 행·입력 fingerprint는 다시 처리하지 않는다. 재검수는 단일 작업 lease로 실행하고, 입력·관리자 수정·정책 중지를 완료 시 다시 확인한다. 만료된 외부 작업은 실패로 남겨 공급자를 재호출하지 않는다. 저장 응답 유실도 공급자를 다시 호출하거나 반대 결정을 보내지 않는다.

재검수는 읽기 전용 로컬 원본을 우선 사용한다. 원본 파일이 없는 운영 환경에서는 DB에 보존된 원본 상호·추출 근거·리뷰·주소·메타데이터를 사용하고, 기존 수집기로 영상 한 건의 자막을 작업 소유 임시 폴더에 가져온다. 필요한 근거가 없거나 결과 식별자가 모호하면 실패로 남긴다. 공유 원본·다른 행·영구 스킵 목록은 수정하지 않는다. 기존 Rule·LAAJ 프롬프트·파서·변환기를 사용한다. LAAJ는 기존 Gemini 모델/설정으로 한 번 요청한다. Rule의 기존 공급자 검증 호출은 별도이므로 전체 Gemini 호출이 항상 한 번이라고 주장하지 않는다.

정기 실행은 기존 일일 크롤러에 연결한다. 새 Actions 예약 작업이나 유료 용량을 추가하지 않았다. 신규 영상 3건 상한 안에서 재검수 한 건의 슬롯을 배정한다. 재검수가 없다고 확인되면 신규 영상 3건을 유지하고, 재검수 또는 불확실한 작업이 있으면 신규 영상은 최대 2건이다. `--dry-run`은 자동 운영 변경과 재검수를 실행하지 않는다. 화면은 표시된 동안 60초 간격과 복귀 시 상태를 읽고 실행 결과 변경 시 검수 목록을 갱신한다.

## 모델과 측정

200건의 배치 요청 수는 `ceil(200/b)`다. 배치 1·25·50·100·200을 각 7회, 같은 합성 입력으로 짝지어 실행 순서를 고정 seed로 섞었다. 모두 같은 새 서버 승인 함수다. 기존 브라우저 승인 화면의 전후 성능 비교로 해석하면 안 된다.

| --- | ---: | ---: | ---: | --- |
| 1 | 200 | 410.35 ms | 기준 | — |
| 25 | 8 | 60.41 ms | 85.28% | 84.04–85.28% |
| 50 | 4 | 53.35 ms | 87.00% | 84.77–87.12% |
| 100 | 2 | 52.30 ms | 87.25% | 85.67–88.56% |
| 200 | 1 | 59.26 ms | 85.56% | 82.92–86.92% |

기본 배치 50의 절대 차이는 **−357.00ms**, 요청 수 차이는 **−196회(−98%)**다. 배치 50→100의 추가 감소는 1.05ms·1.97%, 별도 짝 비교의 95% CI는 **−5.35–24.87%**로 유의한 개선을 확정하지 못했다. 더 작은 변경 단위를 유지하는 50건을 기본으로 삼았다. 전역 최적값이나 모든 운영 입력의 최적값을 증명하지 않는다.

환경은 원시 기록의 macOS·ARM·PostgreSQL 17.6, 동일 연결의 Unix socket이다. 35회 모두 200건의 승인 결과 해시가 일치했다. p50/p75/p95와 짝 bootstrap 10,000회 CI는 `restaurant-automation-batch-summary.json`에 있다. 실제 HTTP·운영 DB·화면 지연, 사용자 생산성, ML 정확도, 공급자 비용·토큰 절감, CPU/RSS 개선을 측정한 실험이 아니다. 공식 G003 성능 주장은 성립하지 않는다.

## 증빙과 운영 상태

- 격리 DB 64개 통과: 중복 승인 0, 조건·근거 누락 차단, 단일 lease, 잘못된 토큰·임의 필드 차단, 관리자 수정 충돌, 중지 후 완료 차단, 만료 작업 재호출 방지, 하루·회당 상한, 동시 동일 요청, 롤백과 재시작, 일반 사용자 권한 거부.
- 전체 웹 2,658개 통과·9개 건너뜀·실패 0개. 관련 Python 20개, 관리자 조회·자동 운영 Bun 17개 통과. 프로세스 fixture는 분리 실행하며 기존 단언·시간 제한을 유지한다. 공급자 실패와 저장 응답 유실 재생은 실제 공급자 성공 증빙과 구분한다.
- 합성 브라우저에서 미리보기→시작→실행→이력을 확인했다. 모바일 390px·태블릿 834px 가로 넘침 0. 모바일 첫 네 버튼 높이 36→44px, 새로고침 폭 40→44px 실측. 전체 프로젝트 반응형 완료 증빙으로 확대하지 않는다.
- 운영 DB에 `20261003081915_restaurant_review_automation.sql` 적용. 본문 SHA-256 `1cff7056df006070a76b466a2ad04cf386fdb8d6b868fba491f6cb88a56246e0`; 적용 본문은 수정하지 않는다.
- 기존 맛집 **1,659건** 전후 SHA-256 동일: `559d6f47d2cea418eada61215fc9fb21573205dd1079edb57410bb501693bcc9`.
- 새 RPC 5개 service_role 허용, anon/authenticated 거부, 공개 SECURITY DEFINER 0개. 전용 테이블 4개 RLS, RPC 등록 5개 확인. 기존 전체 DB의 보안 인증을 의미하지 않는다.
- 적용 직후 정책 **꺼짐**, 실행·항목 **0건**. 보호 승격·웹 배포·정책 활성화·실제 일일 작업·재검수 결과의 운영 읽기 확인은 남았다.
