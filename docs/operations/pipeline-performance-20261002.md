# 크롤링·검수 최적화: 구현과 운영 적용안

격리된 후보의 구현·검증·운영 적용 준비를 진행 중이다. 전체 파이프라인 비교와 완료 감사가 남아 있어 목표를 완료로 표시하지 않았다. 운영 DB 마이그레이션, 배포, 원본 데이터 변경은 수행하지 않았다. 기존 모델과 hosted apply 차단을 유지한다.

## 수학적 모델과 실측

성능 증빙은 `apps/web/performance/pipeline-20261002/`에 있다. 현재 코드를 대상으로 한 `summary-current.json`은 p50/p75/p95, 전후 절대값·차이·변화율, 짝지은 bootstrap 95% 구간과 실험 노이즈 기준을 포함한다. 초기 결과 `summary.json`과 기각된·중간 실험도 보존했다. 캐시 손상 복구와 입력 동시 변경 검증을 추가한 뒤 변환을 다시 측정했다.

변환 캐시는 최초 인덱스 구축 비용을 지불한다. `N × 재실행 절감 > 최초 추가 비용`이므로 p75 기준 변경 없는 재실행 2회부터 최초 비용을 회수한다. 최초 실행의 회귀를 숨기거나 전체 실행이 빨라졌다고 주장하지 않는다.

### 저장: 실제 로컬 PostgreSQL RPC 비교

`storage-summary.json`과 원시 파일 3개는 원본 변환 1,329행을 읽고 격리 DB에서 기존 `batch_upsert_restaurants` 함수 본문을 그대로 실행한 결과다. REST 형식의 사전 조회는 로컬 SQL 어댑터를 사용했다. 운영 Supabase의 네트워크 지연이나 전체 카탈로그를 검증한 증빙으로 해석하지 않는다.

동일 trace를 찾은 행은 분류 함수에서 재연결 후보를 사용하지 않는다. 따라서 해당 행의 영상·이름 재조회는 제거하고, trace가 없는 행에만 기존 별칭·모호성 검사를 유지했다. 동일한 데이터는 쓰기를 생략하며, 이를 확인하기 위한 보호 snapshot 조회는 유지한다.

| 조건, 기본 배치 200 | 표본 | p75 전 → 후 | 절대 차이(후−전) | 단축률·95% 구간 |
|---|---|---|---|---|
| 변경 없음 | 14쌍 | 951.98 → 154.26ms | −797.72ms | 83.80% [82.30, 84.99] |
| 입력 5행 변경 | 14쌍 | 1,034.35 → 183.04ms | −851.31ms | 82.30% [74.73, 85.96] |
| 신규 50행 | 14쌍 | 605.26 → 123.43ms | −481.83ms | 79.61% [78.32, 81.65] |
| 커밋 후 응답 유실에서 재시작 | 7쌍 | 648.16 → 117.49ms | −530.67ms | 81.87% [79.82, 84.74] |
| 전체 갱신 | 14쌍 | 1,036.86 → 883.85ms | −153.01ms | 14.76% [−4.20, 26.17]; 불분명 |

두 실행의 짝을 유지해 같은 소스의 결과를 합쳤으며 각 실행 결과도 보존했다. 전체 갱신은 한 실행에서 악화되고 다른 실행에서 개선되어, 합친 95% 구간이 0을 포함한다. 이를 유의한 속도 향상으로 채택하지 않는다.

변경 없는 1,329행에서 사전 조회는 189→27회, 쓰기 RPC는 7→0회, 총 DB 문장은 196→27회(169회·86.22% 감소)였다. 5행 변경에서는 쓰기 행이 1,329→5행, RPC가 7→1회로 줄었다. 조회/쓰기 바이트 지표는 JSON 인코딩 크기이며 실제 wire 전송량이 아니다. 클라이언트 RSS는 전체 실험 프로세스의 high-water mark여서 조건별 독립 최대값으로 비교하지 않는다.

배치 1·50·100·200을 조건별 최소 7쌍 측정했다. 모든 행을 쓰면 RPC 요청 수의 하한은 `ceil(1329/b)`이므로 각각 1,329·27·14·7회다. 배치 크기 그룹이 순서대로 실행되어 그룹 간 지연의 인과적 최적값을 주장할 수 없다. 기존 기본 200과 최대 200을 유지한다.

관리자 보호 fixture 67행의 보호 필드와 기존 ID 보존을 검사했고 위반·누락·중복은 0건이었다. 실제 커밋 후 응답 유실에서 중단, 확인 후 재시작의 재전송 0회, 동시 관리자 수정 보존과 전체 배치 롤백, 201행 RPC 거부 후 쓰기 0건을 검증했다. 운영 DB나 관리자 실데이터를 수정하지 않았다.

읽기는 입력·설정 해시로 재사용하며, 파일 상태 서명 `(device,inode,size,mtime,ctime)`이 달라지면 내용을 다시 해싱한다. 전체 변환 출력 해시가 달라지면 기존 인증을 재사용하지 않는다. 원본 3,307개 파일·23,636,539 bytes의 SHA-256 전후 일치와 변환 1,257건의 전체 결과 해시 일치를 확인했다.

손상된 변환 출력은 손상 원문을 `.history`에 보존하고 검증된 입력으로 재구축한다. 해싱과 파싱 사이의 파일 변경·추가·삭제는 게시 전에 검사하여 기존 출력과 receipt를 유지한다. 신규 그룹의 우선순위와 같은 크기·복원된 mtime의 변경도 검증했다.

영상 실험은 640×360, 8fps, 13초의 합성 영상에서 두 소비자 × 12구간을 실제 ffmpeg 9.0.2로 추출했다. 원래 방식과 48개 프레임의 파일명·바이트 해시가 7쌍 모두 일치했다. 손상 프레임 실험에서 원래 방식은 7회 모두 손상을 그대로 재사용했으며 후보는 7회 모두 복구했다. 이 조건의 속도 비교에서 잘못된 결과를 빠르게 반환한 기준선을 유효한 처리로 해석하지 않는다.

작업 수를 24개에서 프로세스당 최대 4개로 제한하므로 자원과 시간 사이에 교환 관계가 있다. 제한된 자원에서는 `T >= max(임계 경로, 총 작업량/C)`이며 이 변경을 전체 파이프라인 속도 향상으로 주장하지 않는다. RSS는 20ms 이상의 간격으로 관측한 프로세스 트리의 합이다. 공유 메모리를 중복 계산하므로 실제 호스트 RAM 절약량과 같지 않다. 구간마다 Python을 실행하던 중간 안의 CPU·지연 악화도 보존했으며 최종 안은 Node 실행당 하나의 잠금 처리기를 재사용한다.

검수 목록은 50건(최대 200건)과 커서를 반환한다. 통계와 동일 영상 경고는 전체 인덱스를 대상으로 계산한다. 정규화·검색·상태 분류를 서버와 UI가 공유하며, 데이터 버전 변경 시 커서를 폐기한다. 상세 근거는 선택 시 조회한다. HTTP 응답은 private/no-store이며 두 새 RPC는 service_role만 호출할 수 있다.

최초 조회 중 변경은 한 번 재시도한다. 상세 조회는 목록의 revision을 보내고 읽기 전후에 확인한다. 변경되면 상세를 섞지 않고 목록·통계·경고를 다시 조회한다. snapshot은 5만 행·32MiB를 넘으면 전체를 실패시키며 조용히 잘라 반환하지 않는다. 초기 snapshot은 전체 인덱스를 읽는다. 현재 코드의 DB 요청 수는 1,329행 기준 기존 2회에 비해 첫 조회 4회·캐시가 있는 조회 3회로 늘 수 있다. 이는 코드 경로의 계산이며 실제 DB 비용·지연 개선을 측정한 결과가 아니다.

### 자막 수집: 완료 판정과 단일 작성자

원본 자막 1,125개를 읽기 전용으로 검증했다. 비어 있는 7개는 유효한 완료 결과에서 제외하며 1,118개의 본문과 선택 필드가 null인 기존 기록은 보존한다. 초기 검증은 선택 필드 `duration:null` 때문에 74개의 유효한 기록을 추가로 거부했으므로 기각했고 두 초기 원시 결과도 보존했다. 최종 실험의 입력 파일 해시는 전후 일치한다. 영구 스킵 정책(retry_num >= 3)은 유지하며 실제 원본을 재수집하거나 덮어쓰지 않았다.

중복 URL은 처음 등장한 순서를 유지하며 제거한다. 같은 채널의 프로세스는 OS 파일 잠금 획득 뒤 캐시를 다시 확인한다. 공유 실패 대장은 별도 잠금과 atomic rename으로 갱신한다. 잘린 JSONL 끝부분의 바이트를 보존한 채 새 레코드의 줄 경계를 복구하며 빈 공급자 응답을 성공으로 저장하지 않는다. 누락된 필드와 손상된 결과를 구분하고 실패 대장 쓰기 실패를 성공/자막 없음으로 중복 집계하지 않는다.

`transcript-cache-raw.json`의 각 조건은 7쌍이며 총 98회다. Node 24.21.0·macOS arm64에서 모듈과 잠금 처리기를 미리 시작했다. 공급자 응답은 2ms로 설정한 합성 응답, 실제 네트워크는 0회이며 운영 지연·금액 절감으로 해석하지 않는다. Python 잠금 처리기 CPU는 Node CPU 측정에 포함되지 않는다. p50/p75/p95, Node CPU, 호출·출력 행·바이트, 95% bootstrap 구간과 노이즈 기준은 `transcript-summary.json`에 보관한다.

|---|---|---|---|---|
| 변경 없음 | 0.455 → 1.301 ms | +0.846 ms | +186.07% [+92.97, +371.55] | 0 → 0 |

URL 중복 조건에서 요청 수는 `N=25 → U=5`, 제거 비율은 `1-U/N=80%`이고 7쌍 모두 동일했다(고정 fixture 95% 구간 [80,80], 실제 공급자 비용의 구간이 아님). 동시 실행에서 호출은 2→1로 50% 줄었지만 로컬 대기시간은 늘었다. 잠금과 검증은 데이터 보존·중복 호출 제한이라는 제약조건을 충족하기 위한 변경이며 모든 조건이 빨라진다는 주장으로 채택하지 않는다. 5개 빈/잘린 캐시 실험은 각 35개 결과에서 기존 0개→후보 35개 유효 결과였고 속도 우열은 비교하지 않는다. 나머지 조건의 최신 결정적 결과 해시는 모두 일치한다.

재현: `RUN_DAILY_PYTHON=<project-python> <node24> backend/bin/benchmark_transcript_cache.mjs --corpus <read-only-transcript-dir> --output <new-evidence-file>` 후 `python3 backend/bin/analyze_pipeline_performance.py --transcripts`를 실행한다. 증빙 파일이 이미 있으면 덮어쓰지 않는다.

## 검증과 한계

웹 단위 2,620 통과·9 skip, 오케스트레이션 213 통과, 관련 Python 계약·캐시 검사, Node 유틸리티 11 통과, native/compat 타입 검사와 대상 ESLint를 검증했다. PostgreSQL 15.8의 독립 테스트 DB에서 일반·인증 역할 거부, 수정·삭제 갱신, 롤백 보존, 검색 카운터만 변경했을 때 인덱스 보존을 확인했다. 로컬 브라우저 fixture 100회는 오류 0이며 첫 페이지 밖 검색과 상세 조회, 모바일·데스크톱 렌더링을 확인했다.

이 수치는 로컬 실험이다. API 재생에는 실제 DB·네트워크 지연이 포함되지 않는다. 공급자 재생은 1ms의 통제된 응답을 사용한다. 브라우저는 dev 서버의 합성 데이터이며 변경 전 화면 지연과 비교하지 않았다. 24시간 운영 관측과 완전한 G003 scorer/validator 증빙이 없어 공식 운영 개선, 실제 금액 절감, 세계 순위, 실제 ML 정확도 향상을 주장하지 않는다.

추가 검증은 손상·재시작 Python 사례, 실제 쉘/파서의 제한된 항목·API 실패 후 순차 OAuth fallback, ffmpeg 바이트 동등성·두 프로세스의 단일 작성자, 첫 페이지/상세 조회의 revision 경쟁을 포함한다. PostgreSQL 15.8의 새 독립 fixture에서는 권한 거부, 1,127행 읽기, 카운터/롤백 보존, 50,001행과 32MiB 초과 거부, 기본 키 조회 실행 계획을 검증했다. 상세 완료 상태와 남은 범위는 `completion-audit.json`에 기록한다.

초기 격리 쉘 테스트가 기존 `ensure_gemini_cli_oauth_settings`를 호출하여 `~/.gemini/settings.json`을 다시 썼다. 사전 설정 사본이 없어 이전 인증 선택의 변경 여부와 정확한 원상 복구를 증명할 수 없다. 격리 모드에서 해당 쓰기를 차단했고 이후 테스트는 설정 해시의 전후 일치를 확인했다. 현재 설정을 보존했으며 이 문제를 원본 설정 보존의 완전한 증빙으로 표시하지 않는다.

## 운영 적용 순서

1. 현재 후보를 검토하고 보호된 `develop → data → main` 순서로 소스를 승격한다. 이 작업에서는 승격하지 않았다.
2. 새 `20261001172315_admin_evaluation_pagination.sql`을 프로젝트의 정식 로컬 replay와 운영 preview/readback 절차로 적용한다. 기존 마이그레이션은 수정하지 않는다. RPC가 없는 상태에서 새 페이지 조회를 배포하지 않는다.
3. 기존 Python 가상환경·Node 24·npm 11.6.2와 잠금 파일을 사용한다. 원본의 설치된 백엔드 SDK 1.45.0은 변경하지 않았다. 후보에는 선언된 `^2.18.0` 범위의 SDK 2.26.0을 설치했으며 웹은 release lock의 2.18.0을 유지한다. 기본 추론 동시성은 1이다. 실제 프로젝트 제한을 확인한 뒤 `GEMINI_MAX_INFLIGHT`(1–8), `GEMINI_REQUESTS_PER_MINUTE`, `GEMINI_BUDGET_PROJECT`를 설정한다. 프로그램 기본 RPM 30은 공급자의 확인된 한도가 아니다. TPM/RPD와 여러 호스트의 총량은 별도 운영 확인이 필요하다. API 키 수나 CPU 수를 쿼터로 해석하지 않는다.
4. `PIPELINE_FFMPEG_JOBS`와 `PIPELINE_NETWORK_JOBS`는 별도 상한이다. 중첩 프레임 작업은 공유 풀을 사용한다. 워커가 소유한 미디어 캐시는 성공 후 제거하고 실패 시 재시작용으로 유지한다. 기존 사용자가 지정한 캐시는 삭제하지 않는다.
5. 배치 크기는 `PIPELINE_RESTAURANT_BATCH_SIZE` 1–200으로 설정한다. live item 제한은 유지하며 동일 행은 저장하지 않는다. 관리자 보호·조건부 갱신·읽기 확인과 불확실한 저장의 재전송 금지는 유지한다.
6. 운영 후보의 롤백 SHA와 적용 후 SHA·URL을 새로 확보한다. 현재 source/test 증빙을 운영 readback으로 사용하지 않는다.

프로젝트 예산의 기본 상태 파일은 `~/.cache/tzudong/provider-budget.sqlite`로 체크아웃 사이에 공유한다. `GEMINI_BUDGET_PATH` 또는 `TZUDONG_PROVIDER_STATE_DIR`를 사용하는 모든 실행도 같은 상태 저장소에 맞춘다. OAuth fallback 잠금도 이 디렉터리를 공유하며 API 작업을 모두 마친 뒤 순차 실행한다. 호스트 사이의 SQLite 공유로 분산 쿼터를 보장한다고 주장하지 않는다.

## 크레딧 추가 요청

사용자 지시에 따라 Google One 혜택 6 × US$10을 기존 승인된 결제 계정에 적용했다. 새로고침 후 GCP 잔액은 앱에서 약 ₩8.15만으로 표시된다. 리딤 직후 선불 잔액은 0이었다. 자동 충전과 미래 혜택 자동 적용은 꺼져 있다. 이후 사용자의 명시적 승인으로 10,000원 일회 충전과 `tzudong-free-zero` 연결을 완료했다. 새로고침한 프로젝트에서 Tier 1·선불, 결제 화면에서 잔액 10,000원·월 거래 합계 10,000원·자동 충전 OFF를 확인했다. 코드·키·카드 정보는 이 문서에 보관하지 않는다.


추가 실제 검증은 동일한 기존 모델 `gemini-3.7-flash`·temperature 0.1·출력 상한 4096·thinking MEDIUM으로 1회만 실행했다. SDK의 최대 시도를 1로 제한하고 기존 공유 프로젝트 예산을 사용했다. 응답은 3,544.65ms, 입력 24·출력 5·추론 96·합계 125토큰이며 JSON 응답 검증을 통과했다. 표본 1이므로 비교 개선율이나 95% 구간을 제시하지 않는다. `gemini-real-probe-raw.json`은 연결·모델·SDK 검증이며 맛집 평가 정확도나 실제 금액 절감의 증거가 아니다. 모델 요청의 실제 청구액과 프로모션 차감액은 아직 readback하지 않았다.

카드 삭제는 AI Studio와 올바른 대한민국 결제 프로필의 Google Payments 직접 관리 경로를 모두 확인했다. Google Cloud가 유효한 대체 수단 지정을 요구해 완료하지 못했다. 유효한 대체 수단 없이 결제 계정을 닫거나 정지시키지 않았으며 충전·프로젝트 연결을 보존했다. [공식 결제 수단 조건](https://docs.cloud.google.com/billing/docs/how-to/payment-methods), [Gemini 선불 정책](https://ai.google.dev/gemini-api/docs/billing).

이번 추가 범위는 자막 캐시 10개, 기존 자막 실행 11개와 프레임 검사 1개, Python 프로필/전환 31개가 통과했다. Windows 전용 8개는 macOS에서 건너뛴 상태로 Windows 검증이라고 표시하지 않는다. 기존 Windows 전용 검사 하나가 skip 후 본문을 실행하던 문제를 고쳤고 테스트에서 만든 프로세스의 종료를 확인했다. 전체 파이프라인·메타데이터 단계의 완료 기록·통합 속도·운영 관측과 scorer/validator는 아직 완료되지 않았다.
