GEM-F-03 — pool 스냅샷과 SDK descriptor

기존 구현은 marker.getIcon()의 반환 객체를 직접 수정했다. SDK가 복제 객체를 반환하면 수정이 내부 상태에 반영되지 않는 문제가 있었다.

현재 구현은 WeakMap<PooledMarker, MarkerIconLike>를 사용하고 acquire와 update가 동일한 applyIcon을 거친다.

따라서 clone descriptor에 의존하던 비교 결함은 코드 수준에서 해소됐다.

release 시 스냅샷을 삭제하지 않는 것은 그 자체로 결함이 아니다. 같은 물리 마커를 재사용할 때 마지막 렌더 내용을 비교하기 위한 상태이기 때문이다.

또한 버블 교체 시 marginLeft를 복사해 다음 clamp 계산 전까지 기존 위치를 유지한다. 다만 뷰포트 자체가 변경됐을 때 기존 clamp가 새로운 최적 위치라는 뜻은 아니다.

4. 추가로 확인된 위험
REV-F-01 — 루트 교체와 숨김 재적용 사이의 비동기 경계

Severity MEDIUM · CONDITIONAL · SOURCE_OBSERVED

applyIcon의 setIcon 이후 숨김 재적용은 SDK의 실제 DOM 생성 시점에 의존한다.

재현 조건은 다음과 같다.

숨김 상태의 retained marker가 존재한다.

setIcon이 기존 루트를 제거한다.

새 루트 삽입을 다음 작업으로 지연한다.

숨김 재적용 시 getElement()가 이전 루트 또는 비어 있는 루트를 반환한다.

새 루트가 삽입된 뒤 observer가 실제 새 루트를 숨기는지 검사한다.

현재 observer 구현은 이 경계를 방어하려 하지만 실제 SDK 지연 삽입 시나리오의 실행 증거는 없다.

최소 검증: 지연 DOM 교체 SDK fixture에서 aria-hidden, owner attribute, observer 해제 및 unmount 이후 콜백 부재를 검사한다. 현재 증거로 즉시 코드 변경이 필요하다고 확정하지 않는다.

5. EVIDENCE-01 — 검증 도구의 증거 범위

verify-marker-formal.mjs는 11개 mutant를 격리된 복사본에서 실행하도록 작성됐다.

각 mutant에 대해 단순 비정상 종료가 아니라 예상 테스트 실패 문자열을 확인하고, 브라우저 누락·모듈 로드 실패를 탐지 성공으로 인정하지 않는다.

이 검증 설계는 적절하다. 하지만 이번 대화에서 실제 mutation 실행 로그는 확인되지 않았으므로 11개 mutant가 모두 탐지됐다고 판정하지 않는다.

또한 baseline과 restored 검증이 성공하더라도 이는 지정된 테스트·복사본·실행 환경의 일관성을 뜻한다. 전체 애플리케이션, 실제 SDK, 운영 성능의 인증이 아니다.
