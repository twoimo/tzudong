1\. 현재 상태와 기존 증거 인계\
\
\- 현재 저장소·브랜치·워크트리·원격·실행 중인 서비스·배포 상태를 먼저 확인하라.\
\- AGENTS.md, 현재 검증 지침, 관련 성능 보고서와 기존 목표의 미완료 항목을 읽어라.\
\- 원본 워크트리의 편집·미추적 파일·사용자 데이터·진행 중 작업을 보존하라.\
\- 적합한 기존 작업 복제본을 재사용하고, 격리가 필요하면 원본을 초기화하지 않는 방식으로 준비하라.\
\- 과거 기록의 브랜치·SHA·태그·배포 ID를 현재 상태로 간주하지 마라.\
\- 기존 변경 중 이미 반영된 것, 후보 소스에만 있는 것, 실제 실행 검증이 끝난 것과 미검증 항목을 구분하라.\
\
기존 기록에서 재확인할 항목:\
\- warm 60-cycle 종료 heap이 26.70→33.70MB로 증가해 약 +26.2%를 기록했고, 당시 20% guard를 초과했다.\
\- 같은 소스의 A/A 비교에서도 약 22.15% 변동이 관찰됐지만, 이를 근거로 메모리 실패를 면제하지 않았다.\
\- React 재마운트와 모의 지도 생성 감소는 실험실 증거이며 실제 지도 픽셀의 공백이나 물리 기기의 전체 플리커 제거를 입증하지 않았다.\
\- 실제 SDK·공개 데이터 검사와 별개로 Galaxy Chrome·삼성 인터넷 및 충분한 prospective field 검증이 남아 있었다.\
\- scorer·validator의 실행 성공과 성능 증거의 admission·release 판정은 별개였다.\
\
위 수치는 과거 보고 결과다. 원자료·측정 조건·소스 SHA를 연결하고 현재 상태에서 유효한지 확인하라.\

진행 기록에는 항목별로 다음을 남겨라.\
미착수 / 재현 / 수정 / 실험실 검증 / 실제 SDK·기기 검증 / 배포 / field 검증 / 전달 완료\

3\. 메모리 회귀 원인 규명과 수정\
\
3-1. 측정 범위 분리\
\
다음을 가능한 범위에서 구분하라.\
\- JavaScript heap\
\- DOM·이벤트 리스너·타이머\
\- React 상태·구독·컴포넌트 수명주기\
\- 지도·마커·오버레이 인스턴스\
\- 이미지·타일·캔버스·GPU 관련 자원\
\- 브라우저 프로세스 또는 renderer 메모리\
\- 캐시의 항목 수·보유 데이터·회수 시점\
\
서로 다른 메모리 API나 범위를 같은 값처럼 비교하지 마라. 브라우저별로 지원되지 않는 측정은 미측정으로 표시하라.\
\
3-2. 자연스러운 운영 조건의 회귀 검사\
\
\- cold와 warm을 분리하고 같은 탐색·검색·스와이프 순서를 반복하라.\
\- 시작·중간·종료·idle 후 메모리를 같은 시점과 조건에서 측정하라.\
\- 종료값뿐 아니라 피크·시간 추세·반복 횟수에 따른 증가량을 확인하라.\
\- 기존 warm 메모리 guard와 판정식을 확인하고 유지하라.\
\- A/A 변동이 크면 원인을 분리하고 표본·측정 설계를 개선하라.\
\- 결과를 통과시키기 위해 기준선을 바꾸거나 guard를 완화하지 마라.\
\- profiler와 forced GC는 원인 진단에 활용하되 자연 상태의 primary memory guard를 대체하지 마라.\
\- 측정 잡음이 해결되지 않으면 불확실 또는 실패 상태를 유지하라.\
\
3-3. 보유 경로와 자원 회수\
\
\- 분리된 DOM, 해제되지 않은 리스너·구독·타이머, 오래된 closure와 지도 객체의 보유 경로를 조사하라.\
\- 화면 전환·검색 변경·컴포넌트 해제 후에도 남는 참조를 확인하라.\
\- 캐시의 수명과 소유 범위를 명시하고 무제한 증가를 방지하라.\
\- 지도 인스턴스 재사용과 최종 해제의 경계를 구분하라.\
\- 중복 인스턴스를 숨겨 둔 채 플리커만 줄이는 방식으로 메모리 문제를 악화시키지 마라.\
\- 정리 로직이 정상 상태 복원이나 필요한 캐시까지 파괴하지 않는지 검증하라.\
\
3-4. 검색·선택 캐시 회귀\
\
\- 기존 128개 검색 집합 재방문에서 발생한 캐시 회귀를 필수 검증에 포함하라.\
\- 캐시 용량을 늘리는 것만으로 해결했다고 판단하지 말고 hit·miss·퇴출·재계산·보유 메모리를 함께 측정하라.\
\- ID뿐 아니라 이름·좌표·병합 ID 등 선택 판단에 영향을 주는 값의 변경을 반영하라.\
\- 같은 배열이나 객체가 제자리 수정되는 경우도 검증하라.\
\- 선택 결과·안정적인 순서·중복 처리 의미를 보존하라.\
\- 작은 반복 집합과 캐시 용량을 넘는 집합을 모두 비교하라.\
\
검사 통과 시에도 “메모리 누수가 없다”고 일반화하지 말고, 검증한 조건·반복 수·관측 시간에서의 안정성과 한계를 보고하라.\

4\. 렌더링 병목과 플리커 수정\
\
4-1. 원인 분리\
\
플리커를 하나의 현상으로 묶지 말고 다음을 구분하라.\
\- React 재마운트\
\- 지도 provider·인스턴스 교체\
\- 마커·오버레이 제거 후 재생성\
\- 타일 로딩 지연·오류\
\- 컨테이너 크기·표시 상태 변경\
\- hydration·loading shell 전환\
\- 레이아웃 이동\
\- 긴 JavaScript 작업과 프레임 누락\
\- 의도한 전환 효과와 의도하지 않은 공백\
\
현재 소스에서 관련 shell·layout·지도·선택 캐시 경로를 확인하고 재현 로그·프로파일·화면 증거로 원인을 연결하라.\
\
4-2. 동작을 보존하는 수정\
\
\- 불필요한 재마운트와 지도 재생성을 줄이되 필요한 초기화·해제는 유지하라.\
\- 컴포넌트 위치·key·참조 안정성과 상태 전달을 검토하라.\
\- 불필요한 루프·전체 순회·재계산·중복 쿼리·중복 이벤트를 줄여라.\
\- memoization과 캐시는 입력 변경·수명·메모리 비용을 검증한 뒤 적용하라.\
\- 지도 중심·확대 수준·선택·스크롤·이전 탐색 상태를 보존하라.\
\- 로딩·오류·빈 결과를 정상 지도 표시처럼 위장하지 마라.\
\- 기능 변경이나 대규모 구조 교체가 필요하다고 판단하면 실제 병목과 예상·측정 이득을 먼저 제시하라.\
\
4-3. 플리커 판정\
\
\- 빈 타일, 의도하지 않은 마커 공백, 화면 깜빡임과 레이아웃 이동의 판정 기준을 정하라.\
\- DOM 노드나 마커 객체의 존재와 실제 화면 픽셀 표시를 구분하라.\
\- 정상적인 빈 검색 결과나 의도한 전환을 플리커로 집계하지 마라.\
\- 실제 화면 녹화·프레임·시간 정보와 SDK·렌더 이벤트를 연결하라.\
\- 발생 횟수, 노출 시간, 최대 공백, 프레임 지연과 재현 조건을 기록하라.\
\- 캡처·프로파일링 자체가 성능에 미치는 영향을 확인하고 전후 측정 조건을 맞춰라.\
\
“완전히 제거했다” 대신 “명시한 시나리오 N회에서 관측 0회”처럼 관측 범위를 밝혀라.\

\- 기존 기기 사용 보류와 현재 사용 가능 여부를 확인하고 허용된 범위에서 진행하라.\

6-2. 두 브라우저의 독립 검증\

\- Chrome과 삼성 인터넷을 각각 실제 앱으로 실행하라.\
\- User-Agent 변경이나 데스크톱 모바일 에뮬레이션을 삼성 인터넷 실기기 검증으로 표시하지 마라.\

\- 자동화 기능이 부족하면 지원되는 화면·터치·녹화·원격 디버깅 수단으로 실제 동작을 확인하라.\
\- 실행하지 못한 브라우저나 시나리오는 미검증으로 남겨라.\
\
6-3. 실기기 조건과 동작\
\
\- 화면 방향·해상도·배율·주사율·전원·배터리·발열·절전 설정과 네트워크를 기록하라.\
\- 검색·필터·스와이프·지도 드래그·핀치·마커 선택·상세 이동·뒤로 가기를 확인하라.\
\- 주소창·가상 키보드·회전·백그라운드 복귀에 따른 viewport 변화를 확인하라.\
\- 반복 탐색 후 메모리·반응성·지도 상태를 확인하라.\
\- cold와 warm을 분리하고 캐시·로그인·권한 조건을 맞춰라.\
\- 사용자 데이터나 인증을 지우지 않는 방법으로 비교 환경을 준비하라.\
\
브라우저별 입력 반응, 프레임 지연, 공백·플리커, 오류와 상태 보존 결과를 따로 보고하라. 한 브라우저의 성공을 다른 브라우저의 성공으로 확대하지 마라.\

8\. 보호된 소스 승격·운영 배포·재검증\

\- 관련 PR·커밋·동시 변경을 확인하고 중복 PR이나 불필요한 재작업을 피하라.\
\- 충돌은 동작·데이터 계약을 보존하며 해결하고 영향받은 경로를 재검증하라.\
\- 관련 없는 편집·미추적 파일·다른 작업의 변경을 커밋에 섞지 마라.\
\- 강제 푸시, 보호 브랜치 직접 변경, 필수 검사 생략으로 통과시키지 마라.\

8-2. 릴리스 게이트\

\- 현재 소스에 적용되는 필수 테스트·타입·린트·보안·의존성·성능 검사를 수행하라.\
\- 과거 미해결 의존성 문제는 현재 공식 권고·실제 사용 경로·배포 영향으로 재평가하라.\
\- 과거 경고를 현재도 동일하다고 단정하지 말고, 일부 보안 검사 0건을 전체 안전성 증명으로 사용하지 마라.\
\- 성능·메모리 실패와 실제 기기 미검증을 문서에서 지워 완료 상태로 만들지 마라.\
\- 독립적으로 가능한 변경은 진행하되 해당 변경에 필요한 게이트를 우회하지 마라.\

\- 런타임 버전과 실제 제공되는 자산이 의도한 배포와 일치하는지 확인하라.\
\- CDN·브라우저 캐시 때문에 이전 코드가 제공되는 경우를 구분하라.\

\- 롤백 조건과 실행 절차를 명시하고 복구 후 확인할 항목을 준비하라.\

9\. Prospective field 수집과 실제 사용자 평가\
\
목표는 수집 기준을 미리 정하고, 배포 이후 실제 사용에서 발생한 데이터를 전향적으로 수집·평가하는 것이다.\
\
9-1. 수집 계획 사전 정의\
\
수집 전에 다음을 기록하라.\
\- 시작 시각과 대상 배포 SHA\
\- 대상 환경·브라우저·기기군·페이지·상호작용\
\- 주요 지표와 성공·회귀 판정 기준\
\- 표본 포함·제외·중복 제거 규칙\
\- 최소 표본 수와 관측 기간의 근거\
\- 세션·사용자·기기별 의존성 처리 방법\
\- 중단·롤백 조건\
\- 누락·지원하지 않는 지표의 처리 방식\
\
결과를 본 뒤 유리한 표본만 남기거나 기준을 바꾸지 마라.\
\
9-2. 실제 수집 경로\
\
\- 기존 승인된 계측·저장·조회 경로를 우선 활용하라.\
\- 수집 코드 배포, 이벤트 발생, 전송, 저장, 집계와 조회를 각각 확인하라.\
\- 수집 설정이 켜져 있는 것과 실제 데이터가 쌓이는 것을 구분하라.\
\- 배포 버전·브라우저·기기군·측정 시각을 연결하라.\
\- 사용자 원문 검색어·정밀 위치·계정 정보·화면·인증값 등 성능 평가에 불필요한 개인정보를 수집하지 마라.\
\- 샘플링과 전송 비용을 제한하고 계측 자체의 성능 영향을 확인하라.\
\- 내부 테스트·봇·합성 트래픽은 실제 사용자 cohort와 분리하라.\
\
9-3. Cohort와 성과 해석\
\
\- Chrome·삼성 인터넷, 데스크톱·모바일·태블릿을 필요한 범위에서 분리하라.\
\- 전체 방문 수가 충분해도 Galaxy·삼성 인터넷 표본이 부족하면 해당 환경은 미검증으로 남겨라.\
\- 브라우저에서 제공하지 않는 메모리·성능 지표를 0으로 채우지 마라.\
\- 같은 세션의 다수 이벤트를 모두 독립 사용자 표본처럼 계산하지 마라.\
\- 계절성·네트워크·기기 구성·데이터 규모·동시 변경을 고려하라.\
\- 과거 데이터는 참고·기준선으로 사용할 수 있지만 새 prospective cohort로 바꾸어 부르지 마라.\
\- 실험실·자동화·운영 smoke test 결과를 실제 사용자 field 성과로 집계하지 마라.\
\
9-4. 수집 완료와 부족 상태\
\
\- 사전 정의한 조건에 도달하면 실제 데이터를 분석하고 개선·회귀·불확실성을 보고하라.\
\- 표본이나 관측 기간이 부족하면 현재 수집량·부족 범위·필요 조건·다음 분석 시점을 명시하라.\
\- 표본을 채우기 위해 합성 트래픽을 실제 사용자처럼 만들지 마라.\
\- 수집 준비 완료와 field 검증 완료를 구분하라.\
\- 지속 수집이나 후속 실행은 실제 작동하는 계측·작업·예약 수단을 확인한 경우에만 약속하라.\
\- 필요한 field 증거가 부족한 동안 전체 목표를 완료로 표시하지 마라.\
