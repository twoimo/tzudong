## 재현한 문제

1. 한 번 검사한 고유 목록에 중복을 push하면 WeakSet만 보고 재검사를 생략했다.
2. 보이는 식당의 이름·좌표를 바꿔 검색 대상과 같아져도 이전 순서를 반환했다.
3. 보이는 식당의 병합 ID를 바꿔도 이전 순서를 반환했다.
4. 카탈로그의 다른 식당 좌표가 바뀌어 가까운 후보가 달라져도 이전 후보를 반환했다.
5. 카탈로그에서 cached 후보를 splice로 제거해도 그 객체를 반환했다.

각 기대값은 고정했고, 새 배열로 정상 재계산한 결과도 기대값과 비교했다. 추가 unit8사례는 위 변경과 ID 변경·중첩 병합 ID 변경·같은 선택 필드의 새 객체 교체·배열 재정렬·동일 입력 재사용을 검사한다. 기존 빈 입력·동률·좌표 오류·순서·검색 필드 무효화·64개 용량 검사도 통과했다.

## 변경과 비용

배열을 참조하는 WeakMap에 식당 객체 참조와 선택 판단 필드(id/name/lat/lng/merged IDs)의 스냅샷 하나를 둔다. membership·순서·객체·값이 달라지면 해당 목록의 dedupe/정렬/대체후보 캐시를 함께 무효화한다. visible 목록은 항상 확인하고, 전체 카탈로그는 실제 대체후보 계산이 필요한 경우에만 확인한다. 배열·객체·스냅샷이 도달 불가능해지면 WeakMap의 항목도 회수 대상이다. 회수 시간이나 누수 부재를 실측했다고 주장하지 않는다.

N이 관련 목록 길이, M이 그 안의 병합 ID 수라면 새 검증은 호출당 O(N+M), 관련 live 목록당 추가 스냅샷 공간도 O(N+M)이다. 변경되지 않은 입력은 기존 결과 객체를 그대로 반환하고 재정렬·전체 fallback 스캔은 재사용한다. 검색 이력 상한64는 늘리지 않았다.128검색 재방문의 miss/퇴출·브라우저 비용을 해결했다고 주장하지 않는다. 추가 검증·메모리 비용은 기존 자연 회귀 guard로 다시 검증해야 한다.

## 재현과 남은 검증

격리 checkout에서 Before275fb4be/After0620b97d를 확보하고 두 reproduce 스크립트의 절대 source root를 각 checkout으로 맞춘다. Bun1.4.0으로 실행하면 Before exit1/5실패, After exit0/0실패를 기록한다. raw파일은 wx로 보호하므로 새 실행은 새 evidence폴더와 파일명을 쓴다. `bun test tests-unit/swipe-render-cache.test.ts tests-unit/mobile-home-search-selection.test.ts`가 관련 검사다. source.patch에는 두 파일만 포함된다.

대상 ESLint/diff검사도 통과했다. 현재 진행 중인40프로세스 조건을 보존하기 위해 이 후보의 로컬 production build·typecheck를 동시에 돌리지 않았다. 별도 cloud CI, 이후 실제 UI의 데이터 갱신·선택·스와이프·128검색 재방문·빈 결과·회귀·최종 통합 재측정이 필요하다. 단위 검사 성공을 브라우저·배포·field 성공으로 사용하지 않는다. 운영 DB·미디어·배포·인증·휴대폰 변경은0이다.
