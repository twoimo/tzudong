제공된 소스만 정적 검토한 결과, **잠재적 타인 미디어 삭제 1건, 정리 작업 중단 위험 2건**을 확인했습니다.

### 1\. \[높음\] 삭제 대상과 미디어 소유권 연결 검증 누락

**위치**

- apps/web/lib/admin/record-action-service.ts:90-103
- backend/supabase/migrations/20261009091342\_admin\_record\_private\_verification\_cleanup.sql:24-43,175-201

**문제:** objectName은 경로 형식만 검사합니다. 경로에 포함된 리뷰 UUID가 삭제 대상 리뷰와 일치하는지, 소유자 UUID가 실제 리뷰 작성자인지 확인하지 않습니다.

**재현 조건:** 삭제할 리뷰 A의 미디어 필드에 리뷰 B의 유효한 Storage 경로가 저장되고, DB가 이를 정리 작업으로 반환하는 경우입니다. cleanup\_claim이 승인하면 B의 객체까지 삭제할 수 있습니다.

**최소 수정:** DB 작업 생성 시 리뷰 ID·작성자 ID와 객체 경로의 일치 여부를 검증하고, 삭제 직전에도 신뢰할 수 있는 소유권 정보와 대조해야 합니다.

단, 기존 DB 제약이나 RPC 내부에서 동일 검증을 수행하는지는 제공되지 않아 실제 악용 가능성은 확정할 수 없습니다.

### 2\. \[중간\] 미디어 작업 25건 초과 시 전체 정리 중단

**위치**

- record-action-service.ts:90-91
- 20261009091342\_admin\_record\_private\_verification\_cleanup.sql:27-43

**문제:** 검증 사진 하나가 비공개·레거시 공개 버킷의 작업 2건으로 확장되지만, 클라이언트는 전체 작업을 25건으로 제한합니다.

**재현 조건:** 음식 사진 24개와 검증 사진 1개가 허용된 리뷰라면 정리 작업은 총 26건입니다. safeParse가 실패하여 해당 호출에서 삭제 작업을 전혀 진행하지 못합니다.

**최소 수정:** DB에서 허용하는 최대 작업 수와 클라이언트 제한을 일치시키거나, 최대 25건씩 페이지 단위로 처리하고 남은 작업을 이어서 처리해야 합니다.

### 3\. \[중간\] 객체 조회 오류 하나로 후속 정리 작업 중단

**위치**

- record-action-service.ts:93-108

**문제:** 특정 객체의 storage.exists()가 실패하면 즉시 예외를 발생시켜 이후 작업을 실행하지 않습니다.

**재현 조건:** 첫 번째 공개 버킷 객체의 메타데이터 조회가 일시적으로 실패하면, 뒤에 있는 정상적인 비공개 버킷 작업도 처리되지 않습니다.

**최소 수정:** 작업별 오류를 격리하고 실패 작업의 불확실성을 유지하면서 독립적인 후속 작업을 처리해야 합니다. 최종 결과에는 미완료 상태를 유지해야 합니다.

### 정상적으로 확인된 방어

- 삭제 대상 버킷은 review-photos, review-verifications로 제한됩니다.
- inflight·uncertain 작업에 대한 자동 재삭제를 방지합니다.
- 삭제 응답이 유실되어도 Storage 부재를 재확인한 뒤 완료를 기록합니다.
- 비공개 검증 사진과 기존 공개 버킷의 검증 사진을 각각 처리합니다.
- Storage 삭제 전에 DB의 적용 완료 상태와 작업 선점을 확인합니다.

### 검토 범위 및 결론

**가장 중요한 수정 대상은 1번 소유권 검증입니다.** 실제 데이터 삭제 경계를 보호하는 핵심 조건입니다.

이번 검토는 제공된 텍스트만 사용했습니다. 테스트 실행, 파일 접근, 외부 서비스 호출 및 데이터 변경은 수행하지 않았습니다.

기존 DB 제약, RPC 전체 구현, 트리거 설치 상태와 실제 Storage 동작은 확인되지 않았으므로 운영 환경에서의 결함 재현 여부는 미검증입니다.
