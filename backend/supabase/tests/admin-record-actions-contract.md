# Guarded admin record actions (source only)

The shared browser DTO is `apps/web/lib/admin/record-action-contract.ts`. No browser receives a privileged client, actor override, raw database error, or storage object name. Page/form wiring belongs to the UI owner.

Use `POST /api/admin/record-actions` with one stable UUID:

```json
{"phase":"preview","operationId":"<uuid>","action":"restaurant.edit","targetIds":["<uuid>"],"payload":{"changes":{"phone":"02-1234-5678"}}}
```

The response is `{success:true, receipt}`. After showing the proposed fields and receipt's current IDs/statuses, require the exact confirmation `변경 적용`. Apply sends the *same original request*, changing `phase` to `apply` and adding `previewHash: receipt.previewHash` and `confirmation: "변경 적용"`. Keep the original target IDs (creation/group additions return new IDs in the result). Preview lifetime is 15 minutes; it is not a data retention period. A stale/expired preview requires a new UUID and another review.

After any uncertain response, use `GET /api/admin/record-actions?operationId=<uuid>`. Never silently create a new UUID or resend an uncertain mutation. A committed operation returns its original bounded receipt even after later edits; its receipt describes that transaction, while the UI should separately reload current rows. The SQL stores payload SHA and row fingerprints, not payload copies. It serializes each operation ID, binds actor/action/targets/payload, and commits changes, minimal audit and receipt atomically. Table locks use a deterministic order and a two-second lock timeout; no provider/storage call runs inside the transaction.

`changes` uses existing database field names: `approved_name`, `phone`, `categories`, `youtube_link`, `tzuyang_review`, addresses, `address_elements`, `lat`, `lng`, `geocoding_success`, `youtube_meta`. Geo confirmation must set `geocoding_success:true`; links are canonical HTTPS watch URLs. Categories use the exported canonical array. Never send `status`, `evaluation_results`, provenance, trace ID or admin IDs. Existing actual evaluation grounds remain unchanged. Business telephone fields are narrowly validated as domain data and omitted from the privacy diagnostic scan; arbitrary nested phone fields, notes, metadata and other strings still pass the central sanitizer. No telephone is copied to audit.

Group editing maps `AdminRestaurantModal`'s common fields to `changes`, existing video/review pairs to `perTargetChanges`, deleted IDs to `removeIds`, and new video rows to complete `additions`. This is one CAS transaction over final row identities: swapping two video IDs is supported, and partial repair does not require an already complete row. Empty common `changes` is allowed when explicit per-row edits/removals/additions exist. Approval and creation still require complete domain data. Merge snapshots include existing same-identity/address link rows (maximum 25); later changes to any of them invalidate the preview. Merge does not promote a pending link to approved or synthesize evaluation scores. Submission approvals reuse the existing domain RPCs through a trusted service-role compatibility bridge for modern JSON JWT claims. The wrapper composes omitted fields and nested metadata from the saved row before calling replacement-style legacy RPCs; a single failed item rolls back every preceding item. Existing fuzzy duplicate policy is retained and returns `RECORD_ACTION_DUPLICATE_REVIEW`, a domain-review conflict, not a claim that CAS changed.

For a successful review deletion with `mediaCleanupPending:true`, call `POST /api/admin/record-actions/media-cleanup` with `{operationId}`. Review counts retain the canonical **all reviews** meaning across approve/reject/delete. External/noncanonical/shared assets never prevent moderation or DB deletion; `mediaCleanupUnmanaged:true` distinguishes them from actionable pending jobs without exposing paths.

Cleanup binds the object's metadata fingerprint at the delete transaction, and review preview CAS also includes those fingerprints. A per-path transaction lock and private durable cleanup marker span the DB and Storage operations. BEFORE INSERT/UPDATE guards on `public.reviews` and `storage.objects` enforce the invariant even for a privileged writer: once claimed, a retired path cannot gain a new live reference or content version. Ordinary new paths remain usable. A reference or object change that wins before claim excludes the job and marks it unmanaged. This follows the repository's existing G014 storage-write-fence pattern; object bytes are deleted only through Storage, never by SQL. The new private trigger functions have empty search paths and no public/browser/service EXECUTE grant. Claim returns `{claimed:false}` for protected objects; the helper performs no remove in that case or on malformed claim. Inflight/uncertain delete effects are read back without automatic retransmission. An uncertain attempt whose original object remains needs operator reconciliation; this task does not add a blind retry/reset endpoint. Completed path tombstones intentionally prevent later reuse of a deleted upload name.
