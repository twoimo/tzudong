## Confirmed findings

1. **P1 — Service-role submission approvals fail with the normal JSON JWT claims representation.** The wrapper calls the old approval functions (`20261004190259_admin_record_guarded_actions.sql:293–298`). Both old bodies examine only `request.jwt.claim.role` (`20260417_harden_submission_identity_duplicate_checks.sql:50–56`, analogous edit branch). G041 replaces `auth.uid()` with `g041_current_claim_user_id()`, which returns NULL for a service-role claim (`20260804000500_g041_auth_workflow_bridge.sql:87–103`); it does not replace this role test. With `SET ROLE service_role`, `request.jwt.claims={"role":"service_role"}`, and the legacy setting empty, both new and edit approvals return false and the wrapper raises `RECORD_ACTION_SUBMISSION_CONFLICT`. The same payload succeeds only when the fixture's artificial legacy role GUC is supplied. The existing test helper always sets that legacy GUC (`test_admin_record_actions.py:47–48`), hiding the mismatch. The Next service client does not inject it. Fix the service-call auth boundary using trusted server-role/claims semantics while preserving actor validation; cover normal PostgREST claims before claiming completion.

2. **P1 — A valid crawler record without `approved_name` cannot be approved.** `restaurant_review_decision` returns `approve:all_checks_passed` for the reproduced row using its origin/provider name, but the next empty patch (`new SQL:240–245`) reaches `admin_record_validate_restaurant`, which requires a nonempty `approved_name` (`90`). The old page explicitly obtained `getAdminEvaluationApprovalName(record)` and wrote that name during approval (candidate HEAD page lines 1875–1888; same original behavior). All author fixtures start with an approved name. Preserve an existing admin name, otherwise materialize the approved display name from the reviewed snapshot before final validation.

3. **P1 — Merge has been narrowed and loses the original enrichment behavior.** The new branch rejects every pair with different nonempty video IDs (`new SQL:253–255`), though the old merge RPC has no such restriction. It also merely soft-deletes the source and patches the unchanged target (`256–258`). The old RPC preserves populated target fields but fills absent video link, metadata and review, unions the supplied category, and clears source error metadata (`20260410_add_admin_review_merge_rpc.sql:96–136`). A target lacking a video can merge successfully through the old RPC in the independent fixture, but the new RPC fails `INVALID_RESTAURANT`. The DTO accepts only `mergeTargetId`, so there is no `currentRowChanges` or equivalent reviewed source-data path. This is an actual behavior reduction, not something established as safe by the existing distinct-video rejection test.

4. **P1 — Review photo cleanup has a reference race after claim.** `cleanup_claim` checks references and commits an `inflight` marker (`new SQL:163–167`); `resumeRecordMediaCleanup` then calls Storage remove in a separate transaction/request (`record-action-service.ts:78–82`). Actual baseline review INSERT RLS only checks that `user_id=auth.uid()` and permits a new review to reference the claimed object. The fixture inserts such a row as `authenticated` after claim, before the point at which the helper removes the file. There is no review-write exclusion/tombstone invariant keeping the reference check valid through storage deletion. The initial check at delete and another check at claim do not close this interval. A simple additional pre-remove SELECT would still race. Establish a durable shared reference/cleanup contract before removing objects that may be attached concurrently.

5. **P1 — Edit submission approval can erase existing administrator fields that were omitted from the request.** The new DTO permits omitted `phone`; the wrapper passes its changes directly into the old replacement-style RPC. That function writes `phone=v_phone` and replaces `youtube_meta` wholesale (`20260417_harden_submission_identity_duplicate_checks.sql:379–392`). Reproduction: a saved administrator telephone becomes NULL when phone is omitted, and an existing metadata key disappears when a new title is submitted. Evaluation JSON itself survives. A CAS check detects later edits but does not preserve unspecified already-existing fields. Compose a reviewed final target or use field-aware patches; distinguish intentional clearing from omission.

6. **P2 — Review counts disagree with the original trigger contract.** The baseline `update_user_stats_on_review()` increments/decrements restaurant `review_count` for every review INSERT/DELETE (`pre-20260214-public-schema.sql:3833–3880`). The new action overwrites this with `count(*) ... AND is_verified` after every review action (`new SQL:333`). Reproduction with the actual trigger: two pending reviews give count 2, approving one rewrites the count to 1 although two rows remain. Choose and consistently migrate one count meaning; tests without the trigger cannot establish parity. The fixture intentionally adds only the minimal `user_stats` dependency for this trigger, not the complete user statistics subsystem.

7. **P2 — Group edits validate intermediate rows, not the final batch.** Two existing rows of the same restaurant with distinct video IDs cannot exchange those video IDs atomically: the first `admin_record_patch` sees the second row's old identity and raises `DUPLICATE` (`new SQL:228–231`, `100–103`). The final requested state would satisfy the real active identity index. Reproduction includes the real identity functions and partial unique index. The original sequential browser update had similar constraints; this is an unfulfilled batch-edit requirement, rather than proof of a new regression.

8. **P2 — Partial repair of an incomplete pending record is blocked by whole-row completeness.** A DTO-valid telephone-only patch on a pending row missing geocoding fails `INVALID_RESTAURANT` (`new SQL:113–117`). The implementation treats every edit like completed registration. The old main modal itself demanded geocoding, so this is a contract/partial-edit capability gap, not an assertion that every old UI supported partial repair. Decide which repair buttons need to save incomplete progress and validate only their affected fields while keeping approval complete.

9. **Real fuzzy matching exposes another existing approval rejection path.** Two different addresses with pg_trgm similarity >0.9 cause the unchanged approval RPC to reject, even if name and video are different (`old submission SQL:133–146`, edit `362–377`). Equality-only similarity does not model this. The independent fixture demonstrates it with an almost-equal synthetic street address, leaving all rows unchanged. This is an inherited domain policy, not automatically a defect to remove; the UI needs truthful duplicate/conflict handling and tests for same-location multi-video/neighbor scenarios. The new wrapper collapses all false results into `SUBMISSION_CONFLICT`, whose current client text misleadingly says the item changed.

## UI and compatibility observations (source-only)

- On successful operation readback, the page invalidates submissions/requests/reviews/discovery and reloads evaluation rows. The paged loader clears records, warnings, totals, cursor, revision and detail requests before fetching and on failure (`page.tsx:1301–1342`, `1977–1989`). This is positive cache-boundary evidence.
- On an uncertain apply/readback, `record-action-client.ts:110–125,157–172` stays in the modal and issues GET only; no applied callback is fired. On definite STALE, it rejects and the page's error handler only toasts. Neither path invokes the page reload/reset, so old background rows, counts and revision remain. The existing reload-state tests exercise the loader after invocation, not whether uncertain/stale actions invoke it. Decide whether those views must be cleared/marked stale as part of this task.
- `AdminRestaurantModal.tsx:763–769` still enters `assertLegacyBrowserAdminMutationEnabled`; at this snapshot the modal has no `recordActions` wiring. The shared guarded DTO exists but is not evidence that its group-edit/create buttons work. UI is separately owned and may change after this audit.
- The old recommendation HTTP route (`app/api/admin/restaurant-requests/[requestId]/review/route.ts:164–226`) still calls `review_restaurant_request` without the new preview/operation identity. The old restaurant destructive HTTP route (`.../destructive-action/route.ts:64–123`) creates a new correlation UUID on every request and calls its old RPC. Retiring three authenticated RPC grants does not retire these server entry points. This compatibility surface must be resolved before claiming universal Preview→Confirm→Apply→Readback→Audit and lost-ACK protection.

## Verified controls and limits

- Same operation ID concurrent apply and lost-ACK reread produce one audit; payload mismatch, actor mismatch and changed target fingerprints reject. Browser `authenticated` execution of the service RPC rejects even when supplied a real administrator UUID. The route binds actor to `requireAdmin`, and the strict DTO rejects actor overrides.
- New ledger/audit tables contain payload SHA, fingerprints, actor/action/IDs and bounded receipts. No typed/raw payload copy, telephone, address, evaluation body or reason copy was found in those audits. Recommendation domain audit intentionally leaves its note/reason columns NULL. Business fields and notes still live in their intended domain rows.
- An external/legacy photo does **not** prevent the DB review deletion: apply succeeds with `mediaCleanupPending=true`, no cleanup job for that path, and no unsafe removal. Canonical cleanup paths are owner/review bound. Cleanup uncertainty never automatically resends removal; unresolved inflight media requires reconciliation. There is no complete reconciliation workflow for permanently blocked paths in this implementation.
- The fixture is PostgreSQL **17.11** (installed Homebrew), real **pg_trgm 1.6** and pgcrypto, not the author's private 17.6 build and not hosted runtime proof. We reused the author's isolated table/domain setup, installed actual canonical identity helpers/index, the exact G041 auth.uid transformation, selected original review RLS, and the actual review trigger for one test. We did **not** replay the whole production catalog or use actual managed Auth, HTTP PostgREST, Supabase Storage, provider calls, secrets, or external writes. Legacy functions retain fixture ownership/grants; full real ownership/privilege admission remains a separate replay obligation.
- The two old RPC migrations, G041 bridge, baseline, and both old API files above were byte-compared with `/Users/twoimo/.codex/worktrees/d44d/tzudong` and matched exactly. The audit does not infer old behavior from documentation alone.
